# 设计：一个「检查更新」到底该有哪些语义

这份文档把 README 里的思路落到可检查的契约上。代码在 `nou/`，前端在 `web/`。

---

## 1. 数据契约

一个源只需要回答一件事：

```python
Release(version="1.3.0", url="https://…/file/abc", notes="修了 XXX")
```

- `version` 必填，且必须**可比较**（数字段，见 §2）；
- `url` 是给人看的下载页，不是直链——直链会过期、要过反爬、还容易被换成别的包；
- `notes` 可有可无，超长截断（前端不展示大段 Markdown）。

检查结果是另一件事，注意 `ok` 的含义：

```python
Result(ok=True,  current="1.2.0", latest="1.3.0", has_update=True, …)   # 问到了版本
Result(ok=False, current="1.2.0", latest="",     has_update=False, error="…")  # 没问到
```

**`ok` 不是「HTTP 200」，而是「确实拿到了版本信息」。** 整个设计的正确性都压在这个区分上。

## 2. 版本号

只做「semver-lite」：

| 输入 | 解析结果 | 说明 |
|---|---|---|
| `1.10.0` | (1,10,0) | 与 `1.9.0` 比较时更大——字符串比较会反过来 |
| `v1.2` | (1,2,0) | 缺位补 0 |
| `1.2.3-beta.1` | (1,2,3) | 预发布段丢弃 |
| `build-42` | (0,0,0) | 没有点分段，按 0 处理 |

不引入完整 semver：预发布排序、构建元数据的比较规则，在「提示用户去下载」这个场景里没有收益，只会引入 Bug。

## 3. 状态机

```
        ┌───────────── 缓存命中（< ttl）─────────────┐
        │                                            ▼
   [启动] ──► 读源(主→备) ──► 有版本? ──是──► 比较 latest vs current
                                │                    │
                                否                   ├─ 更大 → has_update=True
                                │                    └─ 否则 → has_update=False
                                ▼
                        有上次成功结果? ──是──► 沿用，stale=True, ok=False
                                │
                                否 ──► ok=False，error=各源错误
```

判定表（**这是最容易写错的地方**）：

| 主源 | 兜底源 | 兜底结果 | 结论 |
|---|---|---|---|
| 成功 | — | — | `ok=True`，按版本比较 |
| 失败 | 成功 | 比我新 | `ok=True, has_update=True`（可信，直接提示） |
| 失败 | 成功 | 不比我新 | **`ok=False`**（兜底源可能只是旧，不能宣布「最新」） |
| 失败 | 失败 | — | `ok=False`；有上次成功结果则 `stale=True` 并沿用 |
| 成功 | 失败 | — | `ok=True`（主源已给出答案，备用失败无关紧要） |

第三行是这套方案的核心判断。省掉它，用户就会在源站故障期间看到「已是最新」——一个安全的错觉。

## 4. 缓存

- 默认 **30 分钟**（`CACHE_TTL`）。检查更新不是实时业务；
- 缓存分两种：`last`（上次返回值，含失败）和 `good`（上次成功的快照）；
- **失败不覆盖 `good`**：这样源站抽风时还能靠昨天的结论提示用户；
- 落盘用 `state_path` 指定，写入用「临时文件 + rename」，避免半截 JSON；
- 强制刷新只给「手动检查」用（`force=True`）。

## 5. 前端 UX 规则

| 场景 | 表现 |
|---|---|
| 自动检查，无更新 | 什么都不显示 |
| 自动检查，有更新 | 小标签 + 弹框，**同一版本只弹一次** |
| 自动检查，失败 | 什么都不显示（用户没要求检查） |
| 手动检查，有更新 | 弹框（不管这个版本看没看过） |
| 手动检查，无更新 | 明确反馈「已是最新」 |
| 手动检查，失败 | 明确反馈失败原因，并给手动下载入口 |

「同一版本只弹一次」的键是**版本号**，不是时间：升到新版本后又发现更新的版本，应该再弹。

## 6. 只探测，不执行（默认）

后端只允许打开**白名单域名**的下载页（GitHub / 网盘），否则就是一个「任意 URL 开浏览器」的后门。

```python
_open_url(url)  # 校验 hostname 后缀，再 webbrowser.open
```

## 6.1 如果要自动替换（可选）

`nou/apply.py` 把「两个进程」封好了，但它的前提条件比探测那部分苛刻得多：

| 前提 | 不满足会怎样 |
|---|---|
| 旧文件可改名 | 写不了就只能走 copy，失去原子性 |
| 目标目录可写 | 装 Program Files 时要提权，否则直接失败（模块会提前报错，不会换到一半） |
| staged 与 target 同卷 | 否则只能 copy，中间有个「半新半旧」窗口 |
| 新文件有 sha256 | 没有就是给远程执行开后门 |
| **老版本已含 helper 参数** | 用户手上那个版本如果没有 `--nou-apply-update`，它无法自学更新 |

状态机：

```
主程序                        helper                                新程序
  │ 下载+验哈希                │                                      │
  ├─ 写 plan.json ───────────►│ wait(pid)                            │
  │                          ├─ target → target.old                   │
  └─ exit ◄──────────────────┤ target ← staged（原子 rename）       │
                             ├─ 校验 sha256 ──失败──► 回滚 .old → 退出3 │
                             └─ start ────────────────────────────►├─ cleanup_old()
```

回滚只能发生在「旧文件还在」的时刻。所以 `.old` 不能当场删：`cleanup_old()` 只删
早于 `min_age`（默认 60 s）的备份，新的那一个留给用户下次启动。

启动时看到 `.old` 存在，等于知道「上一次启动前刚换过文件」——可以拿来做「已更新到 vX」。

## 7. 源的实现要点（网盘类）

1. **按字段取，不按变量名取**——一次性令牌的变量名每次都可能不同；
2. **区分三种「没有」**：空目录（正常）、提取码错（不可重试）、页面改版（不可重试）；
3. **下载页域名可能和分享域名不同**——别拿分享链接的 host 拼文件页；
4. **单测用录制的固定样本**，CI 不联网；
5. **页面结构变化要显式报错**，让上层走「未知」分支，而不是返回空版本号。
